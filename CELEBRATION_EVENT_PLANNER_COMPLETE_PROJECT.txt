CELEBRATION & EVENT PLANNER
COMPLETE PROJECT SPECIFICATION
Version 1.0 | Phase-Based Implementation Blueprint

============================================================
1. PROJECT SUMMARY
============================================================

Project name:
Celebration & Event Planner

Project type:
Universal GenAI-powered event planning and management web application.

One-line description:
A smart event-planning assistant that turns a user's event requirements into a personalized, budget-aware, editable plan with a timeline, tasks, resources, and recommendations.

Problem being solved:
Planning events requires people to coordinate budgets, schedules, vendors, participants, resources, and many small tasks. Existing approaches often require separate documents, spreadsheets, checklists, and websites. Generic templates do not always account for the specific event, constraints, budget, or preferences. The proposed system combines AI-generated recommendations with deterministic application logic and an interactive dashboard so users can create, manage, and adapt event plans in one place.

Core product principle:
ONE universal dashboard + ONE shared planning engine + configurable event-specific templates.
Do not build a separate application or duplicate dashboard for every event type.

Intended users:
- Individuals and families
- College and student organizers
- Community organizers and volunteer groups
- Small organizations and professional event organizers

Initial event coverage:
- Weddings and anniversaries
- Birthdays and private celebrations
- College events and hackathons
- Community and social events
- Corporate events and conferences
- Custom events described in natural language

The application should support additional event types through versioned templates and reusable modules, rather than major architectural rewrites.

============================================================
2. GOALS AND SUCCESS CRITERIA
============================================================

Primary goals:
1. Turn a small set of user inputs into a useful event plan.
2. Generate relevant plans based on event category and user context.
3. Suggest budget allocations and identify budget overruns.
4. Generate preparation timelines, milestones, tasks, and checklists.
5. Recommend themes, activities, menus, and arrangements where relevant.
6. Allow users to edit plans and regenerate selected sections.
7. Save plans and display them in a clear, usable dashboard.
8. Validate AI output and use ordinary code for calculations and constraints.
9. Demonstrate reliability, security, efficiency, testing, accessibility, and maintainable code.

MVP acceptance criteria:
- A user can create an event with title, event type, date, location, currency, budget, expected attendance, duration, and preferences.
- The system offers at least five initial event templates and a custom-event path.
- The system generates structured AI output for an event.
- The output includes an overview, budget proposal, tasks, timeline, and relevant event-specific modules.
- Backend validation prevents malformed AI output from being blindly saved.
- Budget totals are calculated by application code and discrepancies are flagged.
- Users can view, edit, complete, and track tasks.
- Users can update event details and request a plan revision.
- The dashboard only displays specialized modules relevant to the selected event.
- Core data persists in MongoDB and remains available after refresh.
- API keys are not exposed to the browser or committed to source control.
- Essential user flows have automated tests.
- The application can be deployed using documented instructions.

Do not claim that a feature is implemented until it exists and has been tested. Keep planned features clearly separated from completed features.

PHASE 3 — GENAI PLANNING ENGINE AND ADAPTIVE EVENT TEMPLATES

Purpose:
Implement the core intelligence that generates event-specific plans while keeping calculations and validation deterministic.

Expected work:
- Integrate one actual LLM provider selected for the project, such as Gemini or Groq. Do not claim multiple providers unless they are implemented.
- Use a provider adapter so provider-specific code does not leak into domain logic.
- Read the API key only from server-side environment variables.
- Implement a planning orchestrator with clear stages:
  1. Load event and template.
  2. Normalize inputs and identify missing required fields.
  3. Build a constrained prompt using the event context and template.
  4. Request structured output.
  5. Parse and validate output using a schema.
  6. Check business rules and deterministic calculations.
  7. Retry/repair invalid output a bounded number of times.
  8. Save a new plan version only after validation.
  9. Return a normalized response to the frontend.
- Define a strict structured output schema for:
  - Event summary and assumptions
  - Budget categories and estimated amounts
  - Tasks with priority, relative timing, duration, and dependencies
  - Timeline/milestones
  - Recommendations and optional ideas
  - Template-specific modules
  - Warnings and missing information
- Require the model to state assumptions and distinguish estimates from verified quotations.
- Never let the model invent real vendor availability, verified market prices, legal permissions, or confirmed bookings.
- Implement event-aware planning for the five initial templates.
- Implement custom-event classification/proposal with sensible fallback behavior when classification is uncertain.
- Make module visibility data-driven from the template and validated plan.
- Use application code for totals, currency handling, date calculations, dependency checks, and constraint enforcement.
- Implement budget validation and warn if category totals do not match the total budget or exceed it.
- Implement timeline validation for missing dates, impossible deadlines, and dependencies.
- Implement plan revision so users can request changes to relevant sections without unintentionally replacing unrelated saved information.
- Preserve the previous valid plan if the provider fails or returns invalid data.
- Add provider timeouts, bounded retries, rate limits, and clear failure messages.
- Add tests with mocked provider responses for valid JSON, malformed JSON, provider timeout, budget overrun, missing fields, and plan revisions.

Suggested generation API:
- POST /api/v1/events/:eventId/plans/generate
- POST /api/v1/events/:eventId/plans/:planId/revise
- GET /api/v1/events/:eventId/plans/:planId

Example output shape (illustrative only; define and enforce the real schema in code):

    }

  "modules": ["registrations", "teams", "judges", "sessions", "equipment"],
  "warnings": []
}

4. SYSTEM ARCHITECTURE
============================================================

Recommended architecture:
- Frontend: Next.js App Router, TypeScript, Tailwind CSS, reusable accessible UI components.
- Backend: Node.js, Express, TypeScript.
- Database: MongoDB with a maintained ODM or well-defined repository layer.
- GenAI: one provider (Gemini or Groq) through a server-side adapter.
- Validation: Zod or equivalent runtime schemas.
- Charts: Recharts or equivalent.
- Testing: Vitest/Jest plus API integration testing and selected end-to-end tests.
- Hosting: Vercel for frontend; Render or an equivalent Node-compatible host for backend; MongoDB Atlas for persistence.

Architecture flow:
Browser
  -> Next.js UI
  -> Express API
  -> Authentication / Authorization / Request Validation
  -> Domain Services
       -> Event Service
       -> Template Registry
       -> Planning Orchestrator
       -> Budget Service
       -> Timeline Service
       -> Task Service
       -> Report Service
  -> Repositories
  -> MongoDB

Planning Orchestrator
  -> Load event + template
  -> Prepare constraints
  -> LLM provider adapter
  -> Parse structured response
  -> Schema and business-rule validation
  -> Deterministic calculations
  -> Save plan version
  -> Return normalized result

Start as a modular monolith. Do not introduce microservices, message brokers, vector databases, or agent frameworks unless a demonstrated requirement justifies them.

7. AI DESIGN RULES
============================================================

The LLM is responsible for:
- Understanding natural-language requirements.
- Proposing suitable plan content.
- Generating task descriptions and recommendations.
- Suggesting budget categories and estimated allocations.
- Suggesting preparation milestones and event-day activities.
- Proposing changes in response to user requests.

Application code is responsible for:
- Authentication and authorization.
- Input validation.
- Currency and total calculations.
- Date arithmetic and timezone handling.
- Task dependency validation.
- Budget constraints and warnings.
- Stable identifiers and database writes.
- Permission checks and external side effects.

AI prompt construction should:
- Include only relevant event context and template instructions.
- Specify a strict output schema.
- Require explicit assumptions and warnings.
- Tell the model not to invent verified vendor prices, bookings, legal approvals, or availability.
- Treat user text and retrieved content as untrusted data.
- Request concise, actionable output.
- Avoid sending unnecessary personal data to the provider.

AI failure handling:
- Set a request timeout.
- Limit retries.
- Validate the provider response.
- Preserve existing valid data on failure.
- Show an actionable error to the user.
- Avoid duplicate plan creation on retry; use request identifiers or idempotency where appropriate.

RAG is not required for the MVP. Add retrieval only when trusted documents or verified external information materially improve planning.

8. SECURITY, PRIVACY, AND ACCESSIBILITY
============================================================

Security:
- Store secrets in environment variables or a secret manager.
- Commit only `.env.example`, never `.env`.
- Validate and sanitize input at the server boundary.
- Apply event-level authorization.
- Use secure authentication and session/token handling.
- Restrict CORS to intended origins in production.
- Apply rate limits to AI generation and other sensitive endpoints.
- Do not log API keys, tokens, or unnecessary personal data.
- Avoid unsafe rendering of model-generated HTML.
- Treat generated output as untrusted until validated.
- Add safe deletion and retention behavior appropriate to the deployed product.

Accessibility:
- Use semantic headings, forms, buttons, and landmarks.
- Label all form fields.
- Provide visible keyboard focus.
- Support keyboard-only navigation.
- Maintain adequate text/background contrast.
- Do not communicate status through color alone.
- Use accessible names and chart summaries.
- Make layouts usable on mobile and at browser zoom.
